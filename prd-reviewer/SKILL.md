# PRD 需求文档审核技能（红字批注模式）

本技能对软件/IT 产品需求文档（PRD）执行系统性的四维度审核，将审核批注**以红色文字直接插入
原始 PRD 文档中**，并在文档最前面生成一个**「问题汇总索引页」**，支持一键跳转到任意问题位置。

> **文档结构**：本 skill 由三部分组成——①审核维度（4 通用质量维度 + 5 角色视角，含编号规则和问题数据结构）②工作流（Step 1-7，含 3 个 🔴 CHECKPOINT：确认审核范围 → 确认问题清单 → 交付确认）③反例黑名单（10 条常见错误速查）。执行时严格按步骤顺序推进，遇到 🔴 CHECKPOINT 必须暂停等待用户确认。

## 审核维度

本技能采用**双轨审核模式**：先进行通用四维质量审核，再从五个跨职能角色视角做专项检查，确保 PRD 对所有相关方都"可读、可用、可执行"。

---

### 一、通用质量维度

**1. 完整性（Completeness）**  编号前缀：`C-`
检查 PRD 是否包含所有必要章节和字段。典型 PRD 应包含：
- 背景/概述（项目背景、目标用户、问题陈述）
- 目标与成功指标（可量化）
- 范围（In Scope / Out of Scope）
- 用户故事或使用场景
- 功能需求（每条有编号）
- 非功能需求（性能、安全、兼容性等）
- 验收标准 / 测试条件
- 约束与依赖
- 时间线与里程碑

**2. 一致性（Consistency）**  编号前缀：`CO-`
检查需求之间是否存在矛盾或冲突：
- 不同章节对同一功能的描述是否一致
- 同一概念是否使用了不同术语（术语混乱）
- 需求 A 是否与需求 B 逻辑冲突
- 优先级或时间线是否前后矛盾

**3. 清晰性（Clarity）**  编号前缀：`CL-`
检查需求描述是否存在歧义或模糊：
- 使用了模糊词汇（"尽快"、"合适的"、"适当的"、"可能"、"大约"、"一般情况下"）
- 需求主语不明确（谁来做？哪个系统？）
- 需求描述过于笼统，无法指导开发
- 缺少具体数值或量化标准
- 存在技术术语但未定义

**4. 可测试性与可行性（Testability & Feasibility）**  编号前缀：`T-`
- 每条需求是否可以被验证或测试？
- 验收标准是否可量化、可观测？
- 需求是否超出技术可行范围？
- 是否存在无法实现或描述自相矛盾的需求？

### 二、角色视角专项审核

对以下五个关键评审角色的核心关注点逐一扫描，发现对应常见问题时即标记为专项批注。

**5. 产品负责人视角（Product Owner）**  编号前缀：`PM-`

| 核心关注点 | 常见问题 |
|-----------|---------|
| 是否符合产品规划？ROI 是否合理？优先级是否正确？ | 需求与整体方向偏离 |

具体检查项：
- 需求是否能清晰说明"为什么要做"，是否有业务价值量化依据（ROI、DAU 影响、收入等）
- 功能优先级排序是否合理，是否与当前阶段产品目标一致
- 是否存在"镀金"（gold-plating）——加入了产品规划未覆盖的功能
- 与竞品/市场定位的关联是否说明
- 是否有明确的上线时间节点与版本规划

**6. 研发视角（Engineering / R&D）**  编号前缀：`RD-`

| 核心关注点 | 常见问题 |
|-----------|---------|
| 逻辑是否闭环？有无技术盲区？数据结构是否明确？接口依赖是否清晰？ | 异常未定义、状态缺失 |

具体检查项：
- 业务流程图/状态机是否覆盖所有分支（成功、失败、异常、超时）
- 是否存在"异常未定义"：只描述成功路径，未说明失败如何处理
- 是否存在"状态缺失"：某一功能在不同状态下（未登录、无权限、数据为空）的表现未说明
- 数据结构、字段类型、数量限制、枚举值是否明确
- 外部接口/第三方依赖是否有明确说明（API 文档、SLA、降级方案）
- 并发、幂等、事务处理等技术约束是否有描述

**7. 设计视角（UI/UX Design）**  编号前缀：`DE-`

| 核心关注点 | 常见问题 |
|-----------|---------|
| 交互流程是否顺畅？信息层级是否合理？是否有极端状态（加载、空、报错）？ | 缺少极端状态设计 |

具体检查项：
- 用户操作路径是否完整，是否包含返回、取消、撤销等逆向流程
- 信息层级是否清晰，主次操作是否区分
- 是否覆盖了所有极端状态：
  - **加载中**（Loading）：首次加载、分页加载、提交中
  - **空状态**（Empty State）：列表为空、搜索无结果
  - **报错状态**（Error State）：网络错误、权限不足、数据异常
  - **超限状态**：内容过长截断、文件过大拒绝
- 响应式/多端适配要求是否说明
- 是否引用了设计规范或组件库

**8. 测试视角（QA / Testing）**  编号前缀：`QA-`

| 核心关注点 | 常见问题 |
|-----------|---------|
| 验收标准是否明确？是否可量化？是否有足够的可测试点？ | 只有功能描述，无边界条件 |

具体检查项：
- 每条功能需求是否有对应的验收标准（AC）
- 验收标准是否可量化、可客观判断（避免"界面美观"、"速度较快"等模糊表述）
- 是否定义了边界条件（输入最大值/最小值、空值、特殊字符、并发场景）
- 是否有性能基准（如"P99 响应时间 < 500ms"）
- 测试数据依赖是否说明（是否需要特定角色、特定数据状态）
- 回归测试范围是否可从需求中推断

**9. 运营/市场视角（Operations / Marketing）**  编号前缀：`OP-`

| 核心关注点 | 常见问题 |
|-----------|---------|
| 上线后如何触达用户？是否有运营配置能力？数据是否可追踪？ | 缺少配置后台或埋点 |

具体检查项：
- 是否说明了用户触达方式（push、banner、邮件、站内信等）及触发条件
- 是否有运营配置能力：文案、图片、开关、A/B 测试、灰度发布等是否可后台配置而无需发版
- 数据埋点是否有设计：关键用户行为（曝光、点击、转化、跳出）是否纳入埋点计划
- 数据看板/报表需求是否说明
- 是否有上线后的运营支持计划（FAQ、客服话术、公告等）
- 是否考虑国际化/本地化需求

## 工作流程

### 步骤一：识别输入类型并读取文档

本技能支持以下四种输入方式，处理策略各不同：

**输入类型 A：上传 `.docx` 文件**
- 直接使用 `python-docx` 读取段落和表格
- 输出文件在原文基础上批注，保留原始格式

**输入类型 B：上传 `.md` 或 `.txt` 文件**
- 调用脚本内置的 `markdown_to_docx()` 或 `plaintext_to_docx()` 转换函数
- 将文件先转为结构化 `.docx`，再进行批注处理
- Markdown 转换支持：`#` 标题、`**bold**`、`*italic*`、`- 列表`、`1. 有序列表`、`\`\`\`` 代码块
- 纯文本转换支持：自动识别编号行（如 `1.`）为加粗标题，缩进行为列表

**输入类型 C：上传 `.xlsx` 文件**
- 使用 `openpyxl` 提取所有工作表内容，合并为文本后转为 `.docx`
- 适合用 Excel 表格形式编写的需求文档

**输入类型 D：用户直接粘贴文本在对话框**
- 无需文件，直接分析用户在消息中粘贴的 PRD 文本内容
- 脚本通过 `raw_text` 参数接收文本字符串，自动判断是否为 Markdown 格式
- 调用 `text_to_docx_temp()` 转换为临时 `.docx`，处理完成后自动清理临时文件
- 输出文件命名为：`粘贴文本_批注审核_{YYYYMMDD}.docx`

读取时记录每个段落的文本内容，以便后续精准定位注入位置。

**步骤一失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 上传文件损坏/加密/无法读取 | 提示用户重新上传或检查文件完整性 | 建议转为 .md/.txt 格式后重新上传 |
| 上传 .xlsx 但内容非需求文档格式 | 尝试提取所有 sheet 内容，展示给用户确认 | 提示用户将需求内容转为 .docx 或 .md 格式 |
| 粘贴文本过短（< 100字） | 提示用户确认是否粘贴完整 | 仅对已有内容做简要分析并说明"文档可能不完整" |
| Markdown 格式不规范（标题层级混乱） | 按文本顺序解析，忽略格式错误 | 当作纯文本处理，丢失格式信息 |
| 文档内容为非中文/非英文 | 尝试识别语言并按对应语言审核 | 提示用户说明期望的审核语言 |

### 步骤一·半：🔴 CHECKPOINT — 确认审核范围

完成文档读取后，**必须**向用户展示识别结果并确认审核范围，**等待用户确认后再继续**：

```
已读取 PRD 文档：{文件名}
文档格式：{docx/md/txt/xlsx/粘贴文本}
文档长度：约 {N} 字 / {M} 个章节

识别到的输入类型：{A/B/C/D}

即将执行 9 维度全面审核（4 通用质量维度 + 5 角色视角）。
是否有需要重点关注的维度或角色？
```

**使用 AskUserQuestion 工具**提供选项：
- 全面审核（9 维度全部执行）
- 仅通用质量维度（完整性/一致性/清晰性/可测试性）
- 指定重点维度（用户自行说明）

**如果用户未回应**：再次询问，不得擅自假设"全面审核"并直接推进。

### 步骤二：系统性分析

按照四个维度逐一分析，为每个发现的问题记录：

```python
{
    "id": "C-001",                    # 编号前缀说明：
                                      #   C-   = 完整性（Completeness）
                                      #   CO-  = 一致性（Consistency）
                                      #   CL-  = 清晰性（Clarity）
                                      #   T-   = 可测试性（Testability）
                                      #   PM-  = 产品负责人视角
                                      #   RD-  = 研发视角
                                      #   DE-  = 设计视角
                                      #   QA-  = 测试视角
                                      #   OP-  = 运营/市场视角
    "dimension": "完整性",             # 对应维度名称
    "role": "通用",                    # 对应角色（通用 / 产品负责人 / 研发 / 设计 / 测试 / 运营市场）
    "severity": "高",                  # 高 / 中 / 低（见下方分级标准）
    "anchor_text": "...",             # 用于定位插入位置的原文关键词（≤30字，足够唯一）
    "location_desc": "第X章 / 表格X", # 供汇总页显示的位置描述
    "problem": "...",                 # 问题描述（一句话）
    "suggestion": "...",              # 修改建议（具体可操作）
}
```

`anchor_text` 是关键：选择问题段落中**唯一性强**的一段原文（10-30字），用于在文档中精准找到插入位置。如果问题是某个章节标题下内容为空，选择该标题文字作为 anchor。

**严重程度分级标准**：

| 级别 | 判定条件 | 示例 |
|------|---------|------|
| **高** | 阻塞核心业务流程、导致数据丢失/不一致、安全漏洞、需求自相矛盾无法实现 | 状态机缺少关键分支、核心功能无验收标准 |
| **中** | 影响用户体验但有变通方案、描述模糊需要澄清、缺少非功能性需求 | 边界条件未定义、极端状态（空/加载/报错）未覆盖 |
| **低** | 锦上添花的改进、术语不够统一但不影响理解、文档结构可优化 | 标题层级不规范、建议补充国际化说明 |

分析时要有判断力：不要为了"有结果"而捏造问题。如果某个维度没有明显问题，直接说明即可。角色视角的问题与通用维度问题可以合并到同一个 issues 列表，统一处理。

**步骤二失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 文档过短（< 500字），可分析内容不足 | 仅分析已有内容，明确标注"文档内容有限，以下维度未覆盖：..." | 提示用户补充文档后重新审核 |
| 某维度完全没有发现问题 | 在汇总中注明"该维度未发现明显问题" | 不要捏造问题，保持诚实 |
| 问题数量过多（> 50个） | 按严重程度排序，仅详细批注 [高] 和 [中]，[低] 仅在汇总页列出 | 告知用户"问题较多，建议分批处理" |
| 文档包含大量表格/图片描述，难以定位 anchor | 使用表格标题或图片描述文字作为 anchor | 在汇总页标注"位置：第X章附近" |
| 9 维度间发现矛盾问题（如完整性说"有"但一致性说"描述不一致"） | 分别记录为独立问题，在建议中交叉引用 | 标注"此问题涉及多维度，建议综合处理" |

### 步骤二·半：🔴 CHECKPOINT — 确认问题清单

完成系统分析后、生成批注文档前，**必须**向用户展示分析结果摘要并等待确认：

```
分析完成，共发现 {N} 个问题：

按严重程度：[高] {h} 个 / [中] {m} 个 / [低] {l} 个
按维度：完整性 {c} / 一致性 {co} / 清晰性 {cl} / 可测试性 {t}
角色视角：产品 {pm} / 研发 {rd} / 设计 {de} / 测试 {qa} / 运营 {op}

TOP 3 高优先级问题：
1. [{id}] {问题简述}
2. [{id}] {问题简述}
3. [{id}] {问题简述}

是否继续生成批注文档？
```

**使用 AskUserQuestion 工具**提供选项：
- 继续生成批注文档
- 调整审核范围（排除某些维度或降低某些问题的优先级）
- 停止，仅需分析报告文本

**如果用户未回应**：再次询问，不得擅自假设并继续执行。

### 步骤三：生成带批注的文档（调用 `scripts/annotate_prd.py`）

使用本 skill 目录下附带的脚本 `scripts/annotate_prd.py` 对原始文档进行处理。脚本封装了汇总索引页生成、红字批注插入、书签超链接创建、排版格式化等全部逻辑。

#### 3.1 执行方式

**推荐方式**：直接调用脚本，传入问题 JSON 和文档路径：
```bash
python scripts/annotate_prd.py --input 原始PRD.docx --issues issues.json --output 批注审核.docx
```

**备选方式**：如果脚本不可用，参考下方代码片段手动编写处理逻辑。

**注意**：基于原始文件的副本进行操作，**不要修改原始上传文件**。

#### 3.2 问题数据准备

将分析得到的问题列表传给脚本（通过嵌入在脚本中的 JSON 数据，或写入临时 JSON 文件）。

#### 3.3 插入问题汇总索引页

在文档**第一页之前**插入一个独立的"问题汇总"章节，包含：

```
【PRD 审核问题汇总】
文档名称 | 审核日期 | 审核结论 | 总计问题数

执行摘要（1-2段文字）

问题索引表格：
| 编号 | 严重程度 | 维度 | 角色视角 | 问题简述 | 位置 | 跳转链接 |
| C-001  | [高] | 完整性   | 通用       | 非功能性需求内容为空         | 第4章 | [->跳转] |
| RD-001 | [高] | 研发视角 | 研发       | 异常分支未定义，缺少失败处理 | 第3章 | [->跳转] |
| DE-001 | [中] | 设计视角 | 设计       | 缺少空状态和加载中的交互说明 | 第5章 | [->跳转] |
...
```

"跳转链接"使用 Word 内部书签超链接（`w:hyperlink w:anchor`），点击后跳转到文档正文中对应的批注位置。

#### 3.4 在原文中插入红字批注

遍历问题列表，对每个问题：
1. 在文档段落中搜索 `anchor_text`（完全匹配或包含匹配）
2. 找到目标段落后，在其**正后方**插入一个新段落，内容为：

```
【审核批注 C-001 | [高] 高优先级 | 完整性】
[!] 问题：XXX
[OK] 建议：XXX
```

该批注段落的所有文字使用红色（RGB: 255, 0, 0）、斜体、字号比正文小1号，并前后加分隔线以便识别。

3. 在该批注段落处设置 Word 书签（`<w:bookmarkStart>`/`<w:bookmarkEnd>`），书签名为问题编号（如 `issue_C_001`）

#### 3.5 书签与超链接的 XML 实现

```python
from docx.oxml.ns import qn
from docx.oxml import OxmlElement

def add_bookmark(paragraph, bookmark_id, bookmark_name):
    """在段落开头插入书签"""
    tag = paragraph.runs[0]._r if paragraph.runs else paragraph._p
    bm_start = OxmlElement('w:bookmarkStart')
    bm_start.set(qn('w:id'), str(bookmark_id))
    bm_start.set(qn('w:name'), bookmark_name)
    bm_end = OxmlElement('w:bookmarkEnd')
    bm_end.set(qn('w:id'), str(bookmark_id))
    paragraph._p.insert(0, bm_start)
    paragraph._p.append(bm_end)

def add_internal_hyperlink(paragraph, anchor_name, link_text):
    """在段落中添加跳转到书签的超链接"""
    hyperlink = OxmlElement('w:hyperlink')
    hyperlink.set(qn('w:anchor'), anchor_name)
    r = OxmlElement('w:r')
    rPr = OxmlElement('w:rPr')
    rStyle = OxmlElement('w:rStyle')
    rStyle.set(qn('w:val'), 'Hyperlink')
    rPr.append(rStyle)
    r.append(rPr)
    t = OxmlElement('w:t')
    t.text = link_text
    r.append(t)
    hyperlink.append(r)
    paragraph._p.append(hyperlink)
    return hyperlink
```

#### 3.6 分页符处理

问题汇总页结束后插入分页符（`\f`），确保原文内容从新页开始。

### 步骤四：排版规范参考

> 本节是步骤三的补充参考。脚本 `annotate_prd.py` 已内置以下排版规则，仅在手动编写时参考。

批注段落的视觉设计：字体颜色纯红色 RGB(255, 0, 0)，与正文相同字体、字号缩小 1-2pt，斜体，左侧红色竖线或淡红背景（FFF0F0），批注前缀格式 `|| [C-001 | [高]] ` 加粗显示。严重程度标识：[高] 红色字体+淡红背景，[中] 橙红色 RGBColor(255, 140, 0)+淡黄背景，[低] 暗红色 RGB(180, 0, 0)。

### 步骤五：执行参考（手动编写时参考）

> 本节是步骤三的补充参考。优先使用 `scripts/annotate_prd.py`，仅在脚本不可用时手动编写。

在当前工作目录基于原始文件的副本进行操作。**不要修改原始上传文件**。

关键技巧——在指定位置**之后**插入段落：
```python
def insert_paragraph_after(paragraph, text, style=None):
    """在指定段落之后插入新段落"""
    new_para = OxmlElement('w:p')
    paragraph._p.addnext(new_para)
    from docx.text.paragraph import Paragraph
    p = Paragraph(new_para, paragraph._p.getparent())
    return p
```

在文档**开头**插入内容（在所有现有段落之前）：
```python
body = doc.element.body
first_child = body[0]
new_para = OxmlElement('w:p')
body.insert(0, new_para)
```

**步骤三/五失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| `anchor_text` 在文档中匹配不到 | 放宽匹配条件：去掉标点/空格后重试；或搜索关键词子串 | 将批注插入到最相关章节标题后方 |
| python-docx 处理特殊格式报错（如含嵌入对象/SmartArt） | 跳过无法解析的元素，仅处理可读取的段落和表格 | 告知用户"部分格式不支持，已处理可读取内容" |

| 书签 ID 冲突（多个问题 anchor 指向同一段落） | 为每个书签生成唯一 ID（问题编号 + 序号） | 合并同位置批注为一条综合批注 |
| 脚本执行超时（文档 > 100页） | 分批处理：每批 20 个问题 | 告知用户文档过大，建议分段审核 |

#### 步骤七·A：应用修改流程（用户选择"是"时执行）

调用 `doc-update-from-feedback` 技能，将审核建议作为"反馈内容"应用到原始 PRD 中。

**输入准备：**

将 prd-reviewer 生成的 issues 列表转换为 doc-update-from-feedback 所需的结构化反馈：

```python
# 从 issues 列表生成反馈条目
feedback_items = []
for issue in issues:
    feedback_items.append({
        "id":         issue["id"],
        "module":     issue["location_desc"],          # 位置描述作为模块
        "feedback":   issue["problem"],                # 问题描述作为反馈
        "suggestion": issue["suggestion"],             # 修改建议直接应用
        "original":   issue.get("anchor_text", ""),   # 原文定位锚点
        "priority":   issue["severity"],
        "type": "modify" if issue["severity"] in ["高", "中"] else "add"
    })
```

**调用方式：**

将上述 feedback_items 作为反馈内容，连同**原始 PRD 文档**（用户上传的那份，非批注版）一起传入 `doc-update-from-feedback` 技能：

```
原始文档：用户上传的 PRD 文件（.docx / .md / .txt）
反馈内容：上方整理好的 feedback_items（结构化列表）
```

**输出规则：**

`doc-update-from-feedback` 技能会生成一份"修改标注版"文档，其中：
- [紫] **紫色文字** = 建议新增的内容 / 修改后的内容
- ~~删除线~~ = 建议删除或替换的原有内容

修改标注版文件保存到当前工作目录的输出位置，命名格式：
`{原文档名}_修改标注_{YYYYMMDD}.docx`

**两份文档的区别说明（向用户解释）：**

| 文档 | 用途 | 标注颜色 | 内容层面 |
|-----|------|---------|---------|
| `_批注审核_` | 审核意见参考 | [红] 红色 | 指出问题，给出建议 |
| `_修改标注_` | 文档修订底稿 | [紫] 紫色 | 直接呈现修改后的文字 |

## 反例与黑名单

**以下行为在审核过程中严格禁止：**

| 编号 | 反例行为 | 正确做法 |
|------|---------|---------|
| A-1 | 为凑问题数量而捏造不存在的问题 | 没有发现问题的维度如实标注"未发现明显问题" |
| A-2 | 对所有问题一律标 [高] 严重程度 | 根据实际影响范围分级：阻塞性=高，影响体验=中，锦上添花=低 |
| A-3 | 用笼统批注替代具体建议（如仅写"建议优化"） | 每条批注必须给出可直接执行的修改建议 |
| A-4 | 擅自修改原文档内容（非用户要求） | 仅输出批注版，修改需用户明确确认后执行 |
| A-5 | 忽略文档中的表格、图片说明文字 | 表格内容同样纳入审核范围，图片说明也需检查一致性 |
| A-6 | 在批注中泄露敏感信息（如内部系统名、API密钥） | 批注内容仅描述问题和建议，不暴露敏感数据 |
| A-7 | 机械套用所有 9 维度，对短文档也产出过长报告 | 根据文档类型和篇幅灵活选择适用维度 |
| A-8 | 跳过脚本，手动用 python-docx 写 XML 生成文档 | 优先使用 `scripts/annotate_prd.py` 确保一致性和可维护性 |
| A-9 | anchor_text 匹配不到时随意插入到文档开头 | 降级到最相关章节标题后方，或在末尾"无法定位"区集中放置 |
| A-10 | 不展示汇总页直接输出批注文档 | 汇总索引页是必需交付物，帮助用户快速掌握全貌 |
