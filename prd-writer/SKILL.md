# PRD 编写助手

## 工作流程概览

```
会话状态检测 → 智能路由（判断模式） → 按需加载模板 → 收集信息 → 生成PRD → 按需加载自检清单 → 输出文档
```

### 三层按需加载架构

本技能的 token 优化核心是**只在需要的时候才加载内容**，分三层：

| 层级 | 内容 | 何时加载 | 大小 |
|------|------|---------|------|
| L0 路由层 | SKILL.md 本文件 | 技能触发时自动加载 | ~180 行（轻量） |
| L1 模板层 | `references/{enterprise\|agile\|incremental}-prd-template.md` | 路由确定模式后，**只读取命中的 1 份** | 每份 ~150 行 |
| L2 自检层 | `references/quality-checklist.md` | PRD 正文写完后、输出文档前 | ~60 行 |

**关键规则**：
1. **不要预读**：路由未确定前，不读任何 L1 文件
2. **不要全读**：三份模板只读命中的一份，节省约 2/3 token
3. **不要早读自检清单**：写作阶段不需要 L2，写完后再加载
4. **同一对话内复用**：如果同一对话中已读过某模板且模式未变，第 2 次及以后**跳过重新读取**，直接沿用上下文中的模板记忆

### 版本管理（同一对话内多次生成）

在同一次对话中，用户可能多次要求生成或修改 PRD。从第 2 次开始，必须处理版本关系。

**首次生成**：
- 文件命名：`[产品名称]_PRD_v1.md`（或 `.docx`）
- 文档内部版本号：V1.0
- 内部记录：`_prd_session = { product: "XXX", mode: "A|B|C", version: 1, file: "XXX_PRD_v1.md" }`

**第 2 次及以后**：先询问用户版本策略（使用 AskUserQuestion 工具）：

> 检测到本次对话已生成过 PRD：`[上一版文件名]`
>
> 1. **覆盖原版本** — 替换现有文件，版本号不变
> 2. **新建版本** — 保留旧版，生成 v[N+1] 新文件
> 3. **局部修改** — 仅修改指定章节，版本号不变但更新修订记录

根据用户选择：

| 选择 | 文件操作 | 版本号 | 是否重新读模板 |
|------|---------|--------|-------------|
| 覆盖 | 删除旧文件，生成新文件同名 | 不变（vN） | 否——沿用上下文 |
| 新建 | 保留旧文件，生成 vN+1 | +1 | 否——沿用上下文 |
| 局部修改 | 读取旧文件，定点编辑 | 不变，更新修订记录 | 否——沿用上下文 |

**版本号同步**：文件名中的 `v1/v2/v3` 必须与文档内部「文档信息」表的版本号一致。新建版本时，修订记录表追加一行。

## 第一步：智能路由

根据用户输入判断应使用哪种 PRD 模式。只有确定模式后，才去读取对应的参考文档。

### 三种模式的识别信号

**模式 A — 企业级 PRD**
适用信号：
- 企业级 B 端产品（管理后台、ERP、CRM、OA、MES 等）
- 大型系统建设（多模块、多角色、复杂业务逻辑）
- 瀑布式或 V 模型开发
- 新产品从 0 到 1 立项
- 用户提到"系统设计"、"整体架构"、"全面规划"

→ 命中后加载：`references/enterprise-prd-template.md`

**模式 B — 用户故事驱动型 PRD**
适用信号：
- 敏捷开发、迭代需求、Sprint 规划
- 现有产品的功能增强或优化
- 二开定制需求
- 快速响应的小型需求
- 用户提到"用户故事"、"迭代"、"Sprint"、"二开"

→ 命中后加载：`references/agile-prd-template.md`

**模式 C — 迭代延续 PRD**
适用信号：
- 用户提供了已有的 PRD 文件（上传文件、粘贴内容、或指定路径）
- 用户提到"二期"、"下一期"、"续写"、"在原有基础上"、"V2"、"Phase 2"
- 用户提到"基于上次的 PRD"、"延续之前的需求文档"
- 用户描述的需求明确是某个已有系统的下一阶段规划

→ 命中后加载：`references/incremental-prd-template.md`

### 路由决策流程

```
1. 用户是否提供了已有 PRD 或提到"下一期/续写/二期"？
   → 是：模式 C（迭代延续）
   → 否：继续判断

2. 用户描述的是全新系统还是现有功能的增改？
   → 全新系统 + 大型/B端/瀑布式：模式 A（企业级）
   → 功能增改/敏捷/小型需求：模式 B（用户故事驱动型）

3. 仍然无法判断？
   → 用一句话询问用户，给出三个选项的简要区别
```

当需要询问时，用这样的方式（简洁、不丢术语）：

> 你的需求适合哪种文档结构？
> 1. **从零开始的大系统**——需要完整的模块规划和架构设计
> 2. **现有产品加功能**——用用户故事描述需求，配验收标准
> 3. **基于已有PRD写下一期**——延续原文档的编号、术语和架构

### 路由确认后的动作

确定模式后，**只读取对应的一份参考文档**，不要读取其他模式的模板：

| 模式 | 读取文件 |
|------|---------|
| A 企业级 | `references/enterprise-prd-template.md` |
| B 用户故事驱动型 | `references/agile-prd-template.md` |
| C 迭代延续 | `references/incremental-prd-template.md` |

这一步很重要——每份参考文档约 100-150 行，只加载需要的那份可以节省约 2/3 的 token 开销。

## 第二步：收集信息

在开始写 PRD 之前，需要收集足够的信息。信息不足时写出的 PRD 一定是空洞的——与其猜测，不如多问一句。

各模式需要收集的具体信息清单在对应的参考文档中。这里只列通用策略：

- 如果用户一次性提供了充足的信息，直接进入写作阶段
- 如果信息不足，分批询问，每次聚焦一个主题（不要一次性抛出所有问题）
- 对于用户没有明确回答的部分，基于行业常识做合理假设，并在文档中用"【待确认】"标记

### 模式 C 的特殊信息收集

迭代延续模式有一个额外步骤：**深度解析原有 PRD**。在收集新需求信息之前，先从已有 PRD 中提取：
- 需求编号体系（如 F-001、US-001）的编号规则和当前最大编号
- 已定义的角色、术语、状态机
- 已有的功能模块划分和接口规范
- 已有的非功能性需求基线

这些信息是保持延续性的基础。具体操作步骤见 `references/incremental-prd-template.md`。

## 第三步：编写 PRD

按对应参考文档中的模板结构编写。以下是适用于所有模式的通用编写原则。

### 通用编写原则

这些原则的共同目标是：让开发、设计、测试人员拿到文档后能直接开工，不需要反复找产品经理确认。

**清晰优先**：用简单直接的语言描述。"系统应在用户点击提交按钮后 3 秒内返回处理结果"比"系统应快速响应"好一百倍。避免使用"等"、"之类的"、"相关"这些模糊词——每次想写这些词的时候，停下来把具体内容列出来。

**完整覆盖**：每个功能都要覆盖正常流程和异常场景。特别注意：
- 状态流转要画完整（不能只画"正常路径"）
- 边界条件要说清楚（最大值、最小值、空值、重复值）
- 权限控制要明确（谁能看、谁能改、谁能删）
- 数据验证规则要完整（格式、长度、范围、唯一性）

**逻辑一致**：前后文不能自相矛盾。如果第 3 章说某个字段是必填的，第 5 章的流程图里就不能出现该字段为空的路径。

**可执行性**：每个需求点都要具体到研发可以直接编码的程度。对比：
- ❌ "系统应支持数据导出功能"
- ✅ "系统支持将当前列表数据导出为 Excel 文件（.xlsx 格式），导出字段包含：订单编号、客户名称、下单时间、订单金额、订单状态。单次导出上限 10000 条，超出时提示用户缩小筛选范围"

**可验证性**：每个需求都应该能写出对应的测试用例。如果你发现某条需求无法设计测试用例，说明它要么太模糊，要么不是一条合格的需求。

**评审友好性**：PRD 不只是写完就结束的，它会经历评审、被测试验证、被研发反馈修改、被拿来核对开发实现。为了让这些下游流程顺畅，每份 PRD 必须包含以下四个评审支撑要素——对应参考文档中有详细格式指引：

1. **文档目录**：放在文档最前面，评审后反馈更新时会在目录下方插入变更摘要，缺少目录则无法定位。
2. **细粒度需求编号**：模块级编号（F-001）之下，每条具体需求项再分配子编号（F-001-01、F-001-02...），用于测试用例关联和精确定位反馈。
3. **UI 交互状态规范**：每个有交互的功能，都要描述按钮/表单/列表的各种状态（正常态、加载态、禁用态、空态、错误态），这是 UI 还原度测试中"交互逻辑"维度的核查依据。
4. **文案清单**：列出页面上所有文字内容（按钮文本、提示语、报错信息、占位符、空状态文案），UI 还原度测试中的"文案一致性"维度直接核对这张清单。

### 常见陷阱（写作时主动规避）

- 只描述"怎么做"不描述"为什么做"——缺少业务价值说明会让研发团队无法做合理权衡
- **没有 In-Scope/Out-of-Scope 边界说明**——导致研发和产品对"做什么"的理解产生分歧，是评审中最常见的争议源
- **缺少可量化的成功指标**——"提升效率"不是指标；"用户完成操作时间从5分钟缩短到1分钟"才是
- **使用模糊词汇**——`prd-reviewer` 技能会直接标红以下词：「尽快」「合适的」「适当的」「可能」「大约」「一般情况下」「相关」「等」。写完后搜索一遍这些词，把每一处都替换成具体数值或明确表述
- 状态机不完整——必须覆盖成功路径、失败路径、异常路径、超时路径四个分支，只画成功路径是最常见的遗漏
- **未定义权限/登录边界状态**——"未登录"、"无权限"、"数据为空"这三种状态下每个功能的行为是研发最常问、文档最常缺的内容
- **没有边界条件**——输入字段的最大值、最小值、空值、特殊字符、并发场景是测试必查项，PRD 不写就靠开发自由发挥
- 数据验证规则不完整——前端验证和后端验证要分别说明
- 用户故事缺少验收标准，或验收标准不可测试
- 接口设计只有字段列表没有示例数据；外部依赖接口未说明 SLA 和降级方案
- **没有数据埋点设计**——关键用户行为（曝光、点击、转化、跳出）如果 PRD 不写，研发不会主动加；上线后发现无法归因，返工成本极高
- **没有运营配置能力说明**——文案、图片、功能开关如果需要运营配置，必须在 PRD 里说明哪些字段要做成后台可配置；否则每次改文案都要发版
- **UI 交互状态未覆盖空态和错误态**——这两种状态最容易被开发遗忘，测试时却必查
- **没有文案清单**——导致文案在开发和设计之间口头沟通，上线后经常和设计稿不一致
- **没有子需求编号**——测试反馈和评审意见无法精确引用到具体需求条目，沟通成本高

## 第四步：输出文档

### 文件命名

文件名必须包含产品名称和版本号：

```
[产品名称]_PRD_v[版本号].md
[产品名称]_PRD_v[版本号].docx
```

示例：`[产品名称]_PRD_v1.md`、`[产品名称]_PRD_v2.docx`

### 输出格式

默认生成 Markdown 文件。如果用户需要 Word 文档，按以下步骤生成：

1. 先完成 Markdown 版本的内容
2. 使用 docx 技能生成格式化的 Word 文档
3. Word 文档应包含：目录、页眉页脚、版本信息表、合理的标题层级

询问用户偏好的输出格式时，简单问一句即可："需要 Word 文档还是 Markdown 就行？"

## 第五步：质量自检（按需加载 L2）

PRD 正文写完后，**此时才读取自检清单文件**：

```
→ 读取 references/quality-checklist.md
```

按清单逐项核对已生成的 PRD 内容。如果发现缺失项，在输出前补全。

**不要在写作阶段提前读取此文件**——写作阶段应参考 L1 模板即可，自检是独立的最终把关步骤。

自检完成后输出文档，并向用户简要报告自检结果（列出通过/未通过的维度）。
