# 迭代延续 PRD 模板

适用于基于已有 PRD（如 1 期）编写下一期 PRD，保持需求编号、术语、架构的一致性和延续性。

## 核心理念

迭代延续 PRD 不是"重新写一份 PRD"，而是在已有文档的地基上盖新楼层。下游团队已经熟悉了 1 期的编号体系、术语定义和架构设计，2 期文档如果突然换了一套写法，会导致沟通混乱和理解成本飙升。

延续性体现在四个维度：
1. **编号延续**：新需求编号接续原有体系，不重复不断号
2. **术语延续**：复用原有术语表，新术语补充进去而非另起炉灶
3. **架构延续**：新模块在原有架构图上扩展，而非画一张全新的图
4. **规范延续**：沿用原有的数据验证规则、权限模型、接口风格

## 目录要求

每期 PRD 都必须包含目录，放在文档最前面。目录下方是评审反馈后插入变更摘要的标准位置，缺失则无法对接 `doc-update-from-feedback` 技能的自动更新流程。

目录结构应延续上一期的章节编号风格，新增章节追加在末尾。

## 操作步骤

### 步骤 1：解析原有 PRD

在写新内容之前，先从用户提供的原有 PRD 中系统性地提取以下信息。这一步不能跳过——没有这些基础信息，延续性无从谈起。

**提取清单**：

| 提取项 | 说明 | 示例 |
|--------|------|------|
| 编号体系 | 功能/需求编号的前缀和**当前最大值** | F-001~F-010，下一期从 F-011 开始 |
| 角色清单 | 已定义的所有用户角色 | 系统管理员、普通用户、审批人 |
| 术语表 | 已定义的专业术语 | "[术语A]"、"[术语B]"、"[术语C]" |
| 模块划分 | 已有的功能模块列表 | [功能模块A]、[功能模块B]、[功能模块C] |
| 状态机 | 各业务对象的状态流转定义 | [业务对象]：[状态A]→[状态B]→[状态C]→[状态D] |
| 接口规范 | API 前缀、认证方式、返回格式 | /api/v1/*，Bearer Token，标准响应体 |
| 非功能基线 | 已承诺的性能/安全等指标 | 响应时间 ≤ 2s，可用率 ≥ 99.9% |
| 权限模型 | 已有的角色-功能权限矩阵 | RBAC，4个角色×20个功能点 |

**编号提取是最关键的一步**，必须找到原有 PRD 中所有功能编号，确认最大值。例如原有 F-001~F-010，则本期新增功能从 F-011 开始，严格顺序递增，不允许跳号。

同时提取子需求编号：如果原有 PRD 已使用 `F-001-01` 级别的子编号，本期新增功能的子需求也必须使用相同格式；如果原有 PRD 没有子编号，可在本期引入，并在文档中注明"本期起启用子需求编号规范"。子需求编号是评审意见和测试用例精确引用需求的基础。

提取完成后，在新文档开头放一个"基础信息摘要"章节，方便读者快速了解延续了哪些内容。

### 步骤 2：收集新期信息

在已有基础上，收集本期需要新增或变更的内容：

1. **本期目标**：这一期的核心目标是什么？和上一期的关系是什么？（扩展、优化、还是修正？）
2. **新增功能**：有哪些全新的功能模块或功能点？
3. **变更功能**：原有哪些功能需要修改？修改原因是什么？（用户反馈、业务变化、技术债务？）
4. **废弃功能**：有哪些功能要下线或替换？
5. **新增角色**（如有）：是否引入新的用户角色？
6. **架构变更**（如有）：是否涉及底层架构或技术栈的调整？
7. **数据迁移**（如有）：已有数据是否需要迁移或转换？

### 步骤 2.5：统一编排编号（写作前必做）

在动笔写任何新功能之前，先把本期所有新增功能列出来，统一分配编号。这一步单独做，是为了防止写作过程中出现跳号或编号混乱。

做法：
1. 确认上一期最大编号（如 F-010）
2. 列出本期所有新增功能点（不论属于哪个模块）
3. 按优先级或模块顺序，从 F-011 开始连续分配，每个功能点 +1

**示例**（原有 F-001~F-010，本期新增 [模块A] 4个功能 + [模块B] 6个功能）：

| 编号 | 功能名称 | 所属模块 |
|------|---------|---------|
| F-011 | [功能名称-011] | [模块A] |
| F-012 | [功能名称-012] | [模块A] |
| F-013 | [功能名称-013] | [模块A] |
| F-014 | [功能名称-014] | [模块A] |
| F-015 | [功能名称-015] | [模块B] |
| F-016 | [功能名称-016] | [模块B] |
| F-017 | [功能名称-017] | [模块B] |
| F-018 | [功能名称-018] | [模块B] |
| F-019 | [功能名称-019] | [模块B] |
| F-020 | [功能名称-020] | [模块B] |

编号规划确认后，后续章节严格沿用此表，不再重新分配。

### 步骤 3：编写新期 PRD

## 文档结构

### 1. 文档信息

| 项目 | 内容 |
|------|------|
| 文档名称 | [产品名称] 产品需求文档（第 N 期） |
| 版本号 | VN.0 |
| 前序文档 | [产品名称] 产品需求文档（第 N-1 期）V[x.y] |
| 作者 | [作者] |
| 创建日期 | [日期] |
| 审批状态 | 草稿 / 评审中 / 已批准 |

**修订记录表**：延续原有修订记录，新版本接续编号。

### 2. 迭代概述

#### 2.1 本期目标与成功指标
说明本期的核心目标和业务驱动因素，以及与上期的关系。

**本期成功指标**（必须量化——`prd-reviewer` 会标红模糊目标）：

| 指标名称 | 上期基线/当前值 | 本期目标值 | 衡量方式 |
|---------|-------------|---------|---------|
| [例：报表生成时间] | [手工2小时] | [系统自动10分钟] | [埋点统计] |

#### 2.2 范围说明
| 范围类型 | 内容 |
|----------|------|
| 本期新增 | 列出新增的功能/模块 |
| 本期变更 | 列出修改的功能/模块 |
| 本期废弃 | 列出下线的功能/模块 |
| **本期 Out-of-Scope** | **明确列出容易被误解为"二期顺手做了"的内容** |
| 不变部分 | 明确说明哪些保持不变 |

#### 2.3 基础信息摘要
从原有 PRD 提取的关键信息汇总（编号体系、角色清单、模块划分等），让读者不需要翻回上期文档就能理解上下文。

### 3. 变更影响分析

这是迭代延续 PRD 独有的核心章节。对每个变更项，分析其对现有系统的影响面。

**变更摘要表**：

| 变更编号 | 变更类型 | 影响模块 | 影响接口 | 影响数据 | 兼容性 | 优先级 |
|----------|----------|----------|----------|----------|--------|--------|
| CHG-001 | 功能增强 | [功能模块A] | /api/v1/[资源路径] | [数据表]新增字段 | 向下兼容 | P0 |
| CHG-002 | 新增模块 | [功能模块B] | 新增/api/v1/[前缀]/* | 新增[数量]张表 | 不涉及 | P1 |

**变更详述**（对每个变更项）：
- 变更原因：为什么要改
- 变更内容：改什么
- 影响范围：哪些现有功能受影响
- 兼容策略：如何保证已有功能不受破坏
- 数据迁移：是否需要数据迁移，迁移方案是什么

### 4. 新增功能设计

沿用原有 PRD 的功能描述格式和编号体系。

**编号规则**：从原有最大编号之后接续。例如原有 F-001~F-010，新增功能从 F-011 开始（见步骤 2.5 的编号规划表）。

每个新增功能的描述结构和详细程度应与原有 PRD 保持一致。如果原有 PRD 用了功能详述表格，这里也用同样格式；如果原有 PRD 用了用户故事，这里也用用户故事。

此外，无论原有 PRD 是否包含，本期新增功能都应补充以下四项（这些是 UI 还原度测试、评审反馈精确定位、运营视角评审的必要依据）：

**UI 交互状态规范**：

| 控件 | 正常态 | 加载态 | 禁用态 | 空态 | 错误态 |
|------|--------|--------|--------|------|--------|
| [控件名] | [说明] | [说明] | [说明或"不涉及"] | [说明或"不涉及"] | [说明] |

**文案清单**：

| 位置 | 文案类型 | 具体文字 |
|------|---------|---------|
| [UI位置] | 按钮文本/提示语/空态文案/错误提示/占位符 | "[精确文字]" |

**数据埋点与运营配置**（`prd-reviewer` 运营视角必查）：

| 埋点事件 | 触发时机 | 关键属性 |
|---------|---------|---------|
| [例：click_report_generate] | 用户点击"生成报表"按钮 | user_id, report_type, date_range |

运营配置说明：[哪些字段需要后台可配置？如果该功能文案/阈值等可能需要运营调整，在此说明哪些做成可配置项]

### 5. 变更功能设计

对需要修改的原有功能，使用 diff 风格说明变更点，让读者一目了然地看到"改了什么"：

**F-015 [功能页面名称]（变更）**

| 变更点 | 原设计 | 新设计 | 变更原因 |
|--------|--------|--------|----------|
| [字段A] | [原状态] | [新状态] | [变更原因说明] |
| [字段B] | [原限制] | [新限制] | [变更原因说明] |

对于复杂变更，补充变更前后的对比流程图。

### 6. 废弃功能说明

| 功能编号 | 功能名称 | 废弃原因 | 替代方案 | 数据处理 | 下线时间 |
|----------|----------|----------|----------|----------|----------|
| F-008 | [旧功能名称] | [替代原因] | [替代方案编号及名称] | [数据处理方式] | [下线时间] |

### 7. 权限变更

在原有权限矩阵基础上，标注新增/变更的部分。建议用标记区分：
- 🆕 新增权限项
- ✏️ 变更权限项
- 🗑️ 废弃权限项

### 8. 接口变更

#### 新增接口
沿用原有 API 的风格（URL 前缀、认证方式、返回格式）。每个接口配请求/响应示例。

#### 变更接口
对修改的接口，说明新增/修改/删除了哪些字段，以及是否向下兼容。

```
# 变更示例
GET /api/v1/[资源路径]/{id}
# 响应新增字段（向下兼容）
+ "[新增字段A]": "[示例值]"  // [字段说明]，可为null
+ "[新增字段B]": [示例值]     // [字段说明]，可为null
```

#### 废弃接口
列出计划废弃的接口和迁移方案。

### 9. 数据变更

#### 9.1 数据库变更
| 表名 | 变更类型 | 变更内容 | 迁移方案 |
|------|----------|----------|----------|
| [数据表A] | 新增字段 | [字段名] [类型] [约束] | [迁移方案说明] |
| [数据表B] | 新增表 | [表说明] | [迁移方案说明] |

#### 9.2 数据迁移计划（如涉及）
- 迁移范围
- 迁移脚本要求
- 回滚方案
- 迁移窗口和影响

### 10. 非功能性需求变更

在原有基线上说明变更：

| 需求类别 | 原有基线 | 本期变更 | 变更原因 |
|----------|----------|----------|----------|
| 性能 | 列表页 ≤ 2s | 不变 | — |
| 并发 | 100 并发 | 200 并发 | 用户规模翻倍 |

### 11. 术语表更新

在原有术语表基础上新增条目，标注"本期新增"。

### 12. 版本规划更新

更新整体产品的版本路线图，标明当前所在位置。

## 写作要点提醒

- 编号绝对不能和原有文档冲突——写完后要核对一遍编号连续性（尤其注意不能跳号）
- **本期 Out-of-Scope 要明确写出来**——迭代 PRD 中最常见的评审争议就是"二期为什么没做 XX"
- **本期成功指标必须量化**——说明本期目标相对上期有何改善，`prd-reviewer` 会标红所有模糊目标
- 变更分析是这类 PRD 的灵魂，不能省略。研发需要知道"改了什么会影响什么"，测试需要知道回归范围
- 保持格式一致性：如果原有 PRD 用表格描述功能，新文档也用表格；如果用用户故事，也用用户故事
- 废弃功能不是简单标个"已删除"——要说明替代方案、数据处理方式、下线时间
- 接口变更一定要标注向下兼容性，这直接影响前后端协作和发布策略
- 数据迁移方案要具体到可执行，包含回滚方案
- **状态机四条路径都要覆盖**：成功、失败、异常、超时——迭代 PRD 中变更功能的状态机尤其需要检查新增分支是否与原有分支冲突
- **边界条件不能只继承上期**——本期新增功能的输入字段要重新定义最大值/最小值/空值/特殊字符/并发场景
- **新增功能的数据埋点不能省**——上期如果没有埋点方案，本期要补上关键行为的埋点设计
- **运营配置能力要说明**——本期新增的配置项要明确标出，避免研发写死代码
- **新增功能的 UI 交互状态规范不能省**——即使原有 PRD 没写，本期也要补上；空态和错误态是开发最常遗漏的两种状态
- **文案清单要精确**——不要写"提示导出成功"，要写 `"导出成功，文件已开始下载"`；文案不精确，UI 还原度测试里"文案一致性"这一项必挂
- **子需求编号是评审闭环的关键**——评审意见写"请修改 F-011-08"，比"请修改[某模块]的文案"精确得多，减少沟通反复
