# PRD 质量自检清单

生成 PRD 后，按以下清单逐项自检。每一项都对应 `prd-reviewer` 技能会检查的九个维度。

---

## 完整性（C 维度）
- [ ] 包含背景/概述：项目背景、目标用户、问题陈述
- [ ] 包含可量化的成功指标（不接受"提升效率"——要写"操作时间从X分钟缩短到Y分钟"）
- [ ] 包含 In-Scope / Out-of-Scope 范围边界说明
- [ ] 每条功能需求都有编号
- [ ] 包含非功能性需求（性能、安全、兼容性，且有具体指标）
- [ ] 包含约束与依赖（技术栈限制、外部系统依赖、时间节点）
- [ ] 包含时间线/版本规划

## 一致性与清晰性（CO / CL 维度）
- [ ] 没有使用模糊词：「尽快」「合适的」「适当的」「可能」「大约」「一般情况下」「相关」「等」
- [ ] 每条需求主语明确（哪个角色？哪个系统？）
- [ ] 前后文没有矛盾之处（同一功能在不同章节描述一致）
- [ ] 专业术语有定义，且全文使用一致

## 可测试性（T 维度）
- [ ] 验收标准可量化、可客观判断（不接受"界面美观"、"速度较快"）
- [ ] 定义了边界条件（输入最大值/最小值/空值/特殊字符/并发场景）
- [ ] 有性能基准指标（如"P99响应时间 < 500ms"）

## 研发视角（RD 维度）
- [ ] 状态机覆盖了所有分支：成功路径、失败路径、异常路径、超时路径
- [ ] 定义了边界状态：未登录、无权限、数据为空时各功能的表现
- [ ] 数据字段类型、长度限制、枚举值已明确
- [ ] 外部接口/第三方依赖已说明（包括 SLA 和降级方案）
- [ ] 并发、幂等性等技术约束已说明（如适用）

## 设计视角（DE 维度）
- [ ] 用户操作路径完整，包含返回、取消、撤销等逆向流程
- [ ] 每个有交互的功能都包含 UI 交互状态规范（正常/加载/禁用/空/错误五种状态）
- [ ] 每个页面/功能都包含文案清单（按钮文本、提示语、报错信息、占位符一一列出）
- [ ] 响应式/多端适配要求已说明（如适用）

## 运营/市场视角（OP 维度）
- [ ] 用户触达方式已说明（如 push、banner、邮件、站内信的触发条件）
- [ ] 运营配置能力已说明（哪些内容需要后台可配置，无需发版）
- [ ] 关键用户行为的数据埋点已设计（曝光、点击、转化等）
- [ ] 数据看板/报表需求已说明（如适用）

## 评审友好性
- [ ] 文档包含目录，章节编号清晰
- [ ] 功能编号已细化到子需求级别（F-001-01 等），每条需求项都有唯一 ID

---

## 模式 C 附加自检

- [ ] 写作前已完成"步骤 2.5 统一编号规划"，所有新增功能编号从原有最大号 +1 顺序分配，无跳号
- [ ] 逐一核对文档中出现的所有 F-xxx 编号，确认与规划表完全一致，无断号、无重复
- [ ] 新增角色/术语已补充到术语表
- [ ] 新增状态与原有状态机的衔接点已说明
- [ ] 变更摘要表准确反映了对原有功能的影响
- [ ] 原有接口的变更标注了向下兼容性
