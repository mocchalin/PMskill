# PRD to UI Prompt

将需求文档转化为高质量的 UI 界面生成提示词。

这个 skill 解决的核心问题是：需求文档里写的是"做什么"和"为什么"，但 UI 生成工具需要的是"长什么样"和"怎么交互"。这个 skill 就是那个翻译层——把产品语言转化成设计语言。

> **文档结构**：本 skill 由三部分组成——①工作流（Step 1-6，含 3 个检查点）②写作原则（写好 prompt 的核心准则）③反例黑名单（常见错误速查）。执行时严格按步骤顺序推进，遇到 🔴 CHECKPOINT 必须暂停等待用户确认。

## 工作流

### Step 1: 读取需求文档

支持以下输入方式：
- 用户上传的文件（.md / .docx / .pdf）
- 用户直接粘贴的文本
- 用户提供的文件路径

读取文档后，提取以下关键信息：
- **产品定位**：这是什么产品，面向谁，解决什么问题
- **功能模块**：有哪些页面或模块，各自的核心功能
- **用户角色**：不同角色看到的界面可能不同
- **数据实体**：涉及哪些数据对象、字段、状态
- **业务流程**：关键流程的步骤和分支
- **非功能需求**：如果有提到设计风格、品牌色、响应式要求等

如果文档内容较薄，缺少关键信息，主动向用户提问补充。

**Step 1 失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 文档无法读取（格式不支持/加密/损坏） | 尝试用 `pdf` skill 或通用文本提取工具；提示用户转换为 .md | 请用户直接粘贴文本内容 |
| 文档内容太薄（少于 200 字/只有标题无细节） | 列出缺失的关键信息（产品定位、功能模块、用户角色等），向用户提问补充 | 告知用户"当前信息不足以生成高质量 UI prompt，建议补充后再继续" |
| 文档是技术文档而非需求文档（API 文档/数据库设计等） | 尝试从中提取用户界面相关信息；告知用户"这是技术文档，UI prompt 可能需要额外的需求说明" | 请用户提供需求文档或功能说明 |

### Step 2: 🔴 CHECKPOINT — 确认目标工具

使用 AskUserQuestion 询问用户目标，**必须等待用户明确选择后再继续**：

**选项 A — UI 设计工具**（Figma、Motiff、MasterGo、即时设计等）
输出偏重视觉层面：布局结构、配色方案、字体排版、组件样式、间距规范。prompt 需要描述"看起来像什么"。

**选项 B — Vibe Coding 工具**（Qoder、Cursor、Bolt、v0、Lovable 等）
输出偏重实现层面：技术栈、组件树结构、状态管理、交互行为、响应式断点。prompt 需要描述"怎么实现出来"。

**如果用户未明确选择**：再次询问，不得擅自假设。不同工具类型的 prompt 风格差异很大，选错方向会导致返工。

确认后，加载对应的参考模板：
- 选项 A → 读取 [references/ui-tool-template.md](references/ui-tool-template.md)
- 选项 B → 读取 [references/code-tool-template.md](references/code-tool-template.md)

### Step 3: 生成整体设计方向 Prompt

在拆分页面之前，先输出一个整体的设计方向 prompt。这个 prompt 的作用是建立统一的视觉和交互基调，避免逐页生成时风格不一致。

整体方向 prompt 应包含以下**独立子章节**（每个子章节用 ### 标题分隔，便于设计师快速定位）：

**产品概述**
- 一句话说明产品是什么、面向谁
- 核心价值主张

**设计基调**
- 视觉风格关键词（如：极简、专业、活力、科技感）
- 情绪板描述（如果能从需求文档中推断）
- 参考的设计语言或风格（如：类似 Linear 的简洁、类似 Notion 的灵活）

**配色方案**（用表格组织，每行包含角色名、色值、用途说明）
- 设计工具需要精确色值才能工作，所以这里必须给出具体 HEX 值
- 至少包含：主色、辅助/强调色、背景色、文字色、边框色、hover/active 状态色
- 如果 PRD 未指定，根据产品定位和行业惯例推断合理的配色

**字体层级**（用表格组织，列出各层级的字体、字重、桌面端字号和移动端字号）
- 至少覆盖：H1 ~ H4、正文、辅助文字、按钮文字、数据展示

**间距与布局基础**
- 页面最大宽度、内容区 padding
- 栅格系统（如 12 列，gutter 宽度）
- 圆角、阴影、边框的全局规范

**通用组件风格**
- 按钮（主要/次要/文字按钮的外观差异）
- 卡片、输入框、标签、徽标等
- 图标风格（线性/面性/双色，推荐图标库）

**交互与动效规范**（集中定义全局交互模式）
- hover/focus/active 状态的通用规则
- 过渡动画的时长和缓动函数
- 滚动行为（如 sticky header、滚动触发动画）
- 核心交互模式（导航方式、弹窗策略、列表/卡片偏好）

**响应式断点**（用表格列出三个断点：桌面、平板、移动端）
- 每个断点的宽度范围和布局策略
- 必须包含平板断点——很多团队会忽略它但实际需要

**无障碍要求**
- 文字对比度要求（WCAG AA：正文 4.5:1、大字 3:1）
- 如果有强调色/浅色背景组合，说明对比度是否达标
- 触控目标最小尺寸（移动端 44x44px）

**页面地图**
- 列出所有需要生成的页面/模块
- 标注页面间的导航关系和入口
- 标注每个页面的优先级
- 明确交付范围（几个画板/版本）

**Step 3 失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 无法推断配色方案（PRD 未指定品牌色/行业不明确） | 根据产品定位和行业惯例给出推荐配色；在 CHECKPOINT 中说明"配色为推断，请确认是否符合品牌规范" | 使用中性灰+蓝色作为默认安全配色，并提示用户后续调整 |
| 页面地图无法确定（PRD 未明确列出页面/模块边界模糊） | 根据功能模块和用户角色推断页面划分；在 CHECKPOINT 中列出推断的页面地图请用户确认 | 告知用户"PRD 中页面划分不明确，建议补充后再继续" |
| 设计基调与产品定位冲突（如 B2B 产品但 PRD 要求"活泼"风格） | 按 PRD 要求生成，但在 CHECKPOINT 中标注风险："此风格可能不符合 B2B 产品调性" | 提供两种方案（PRD 要求版 + 推荐版）供用户选择 |

### Step 3 半：🔴 CHECKPOINT — 确认整体设计方向

整体设计方向 prompt 生成后，**必须**向用户展示并等待确认，再进入逐页生成。这是防止方向跑偏的关键防线——一旦整体方向错误，后续所有页面都会继承错误。

**展示内容**：
```
整体设计方向已生成，核心要素如下：

📋 产品定位：[一句话概述]
🎨 设计基调：[视觉风格关键词，如：极简、专业、科技感]
🎨 主色调：[主色 HEX 值] + [辅助色 HEX 值]
📐 页面地图：共 N 个页面/模块
   - [页面 1]（P0）
   - [页面 2]（P0）
   - [页面 3]（P1）
   - ...

请确认：
- 设计基调和配色是否符合预期？
- 页面列表和优先级是否正确？
- 是否有需要补充或调整的内容？
```

**用户确认后再进入 Step 4**；如果用户指出方向偏差，先调整整体方向再确认。

**如果用户未明确回应**：再次询问，不得直接进入逐页生成。

### Step 4: 逐页面生成详细 Prompt

按页面地图逐一生成。每个页面的 prompt 必须是**独立可用**的——用户可以单独复制一个页面的 prompt 到工具里生成，不需要翻回去看整体方向。

为了做到独立可用，每个 section prompt 内部要**内联引用相关的设计 token**（色值、字号、间距），而不是写"参见整体配色方案"。这是因为用户很可能是逐 section 复制粘贴到 AI 设计工具或 AI 编码工具中使用的。

每个页面 prompt 的结构：

**页面标题和定位**
- 这个页面的核心任务是什么
- 用户在什么场景下到达这个页面

**布局结构**
- 整体布局描述（如：左侧导航 + 右侧内容区）
- 各区域的功能和大小比例
- 关键区域的层级关系

**核心组件**
- 列出页面中的关键组件
- 每个组件的功能、数据来源、交互行为
- 组件之间的联动关系

**数据展示**
- 需要展示哪些数据字段
- 数据的格式和状态（空态、加载态、错误态）
- 提供合理的示例数据（这很重要，生成工具有具体数据时效果好得多）

**交互行为**
- 主要的用户操作和反馈
- 表单验证规则（如果有）
- 状态切换和过渡

**响应式适配**
- 为桌面、平板、移动端分别说明布局变化
- 内容的显示/隐藏/重排策略

**Step 4 失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 页面数量过多（>10 页），一次性生成 prompt 过长 | 按优先级分批生成：先生成 P0 页面，用户确认后再继续 P1/P2 | 告知用户"页面较多，建议分批次生成，每批 3-5 页" |
| 某个页面的 PRD 描述模糊（只有一句话或关键词） | 根据整体设计方向和同类页面推断；在 prompt 中标注"此页面 PRD 描述较简，以下内容为推断" | 跳过该页面，在设计师备注中标注"需补充 PRD 细节" |
| 页面间依赖关系复杂（如列表页→详情页→编辑页） | 在 prompt 中明确标注页面间的数据流和导航关系 | 建议用户确认页面流程，或提供页面流转图 |
| 目标工具模板缺失（references/ 目录下无对应模板文件） | 使用通用 prompt 结构；告知用户"未找到目标工具模板，将使用通用格式" | 请用户提供目标工具的 prompt 示例或规范 |

### Step 4 半：🔴 CHECKPOINT — 审查生成的页面 Prompt

逐页面生成完成后（或分批生成每批完成后），**必须**向用户展示生成结果摘要并等待确认，再进入最终交付。这是防止页面 prompt 偏离需求的关键防线。

**展示内容**：
```
已生成 N 个页面的详细 prompt，摘要如下：

1. [页面名称]（P0）— [一句话描述核心功能和布局]
2. [页面名称]（P0）— [一句话描述核心功能和布局]
3. [页面名称]（P1）— [一句话描述核心功能和布局]
...

待处理：
- [页面 X] 的 PRD 描述较简，prompt 内容为推断
- 页面间数据流：[页面 A] → [页面 B] → [页面 C]

请确认：
- 各页面的功能和布局是否符合预期？
- 是否有需要调整或补充的页面？
- 是否继续生成设计师备注和最终交付文件？
```

**用户确认后再进入 Step 5**；如果用户指出某个页面偏差，先调整该页面 prompt 再确认。

**如果用户未明确回应**：再次询问，不得直接交付。

**Step 4 补充失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 某个页面 prompt 与整体设计方向冲突 | 重新对齐设计 token（色值/字号/间距）；在 CHECKPOINT 中标注"此页面已重新对齐整体方向" | 删除冲突页面 prompt，在设计师备注中标注"需重新设计" |
| 用户要求修改已确认的整体方向 | 回溯到 Step 3 半 CHECKPOINT，重新确认整体方向后重新生成受影响的页面 | 告知用户"整体方向变更将影响已生成页面，建议分批调整" |
| 页面间数据流复杂，prompt 难以描述清楚 | 在 CHECKPOINT 中用流程图或列表形式展示数据流；建议用户提供页面流转图 | 在设计师备注中标注"数据流复杂，建议与产品确认" |

### Step 5: 补充设计师备注

在所有页面 prompt 之后，添加一个简短的"设计师备注"章节，包含：
- 设计稿交付清单（需要交付哪些画板/版本）
- 对设计师的提醒：如需要注意的边界情况、容易遗漏的细节
- 如果是 UI 设计工具方向，提醒 Frame 命名规范和组件复用建议

**Step 5 失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| PRD 中未明确交付范围（需要哪些画板/版本） | 根据页面地图和优先级推断交付清单；在备注中标注"交付范围为推断，请确认" | 列出所有页面，由用户自行决定优先级和交付范围 |
| 无法确定 Frame 命名规范（目标工具不明确） | 使用通用命名规范（如 "Page-Name-State"）；告知用户"命名规范为通用建议" | 省略 Frame 命名建议，仅提醒组件复用 |

### Step 6: 输出和交付

将所有 prompt 整合到一个 Markdown 文件中，结构如下：

```
# [产品名] UI Prompt

## 整体设计方向
[整体 prompt]

## 页面 Prompt

### 1. [页面名称]
[详细 prompt]

### 2. [页面名称]
[详细 prompt]

...
```

保存文件并告知用户。如果页面较多（>5 个），建议用户分批复制到生成工具中使用。

**Step 6 失败模式处理**：

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 输出文件过大（>5000 字/10+ 页面） | 按优先级拆分为多个文件（P0/P1/P2）；告知用户"文件已拆分，建议分批使用" | 保留单文件，但在开头添加"使用建议"章节说明分批使用策略 |
| 用户要求修改已交付的 prompt | 定位到具体页面 prompt 进行修改；告知用户"已更新，请重新复制到工具中" | 建议用户直接在工具中微调，而非修改 prompt 源文件 |
| 用户要求导出为其他格式（非 Markdown） | 尝试转换为纯文本或 HTML；告知用户"Markdown 格式最兼容各类 AI 工具" | 仅保留 Markdown 格式，建议用户使用在线转换工具 |

## 写好 UI Prompt 的关键原则

这些原则背后的逻辑是：UI 生成工具（无论是 AI 设计工具还是代码生成工具）在有具体、明确、可视化的描述时表现最好，而在抽象、模糊的描述时容易跑偏。

**具体优于抽象**
- 差："展示用户信息" → 好："左侧显示用户头像（64px 圆形）和用户名，右侧显示邮箱、注册时间、上次登录时间三行信息"
- 差："一个表格" → 好："一个数据表格，列包括：订单号、客户名称、金额（右对齐）、状态（用彩色标签：待处理-黄色、已完成-绿色、已取消-灰色），支持按列排序"

**提供真实的示例数据**
- 不要说"显示用户列表"，而是给出 3-5 条具体的示例数据
- 示例数据应该有差异性：不同长度的名字、不同状态、不同数值范围
- 这样生成工具可以自然处理排版和边界情况

**描述状态，不只是静态画面**
- 空状态：没有数据时显示什么
- 加载状态：数据加载中如何展示
- 错误状态：出错时如何提示
- 边界情况：数据过多、名字过长、数值为零时怎么处理

**交互用因果句式**
- "当用户点击 [X] 时，[Y] 发生"
- "鼠标悬停在行上时，右侧出现编辑和删除图标"
- 这比"支持编辑和删除"清晰得多

**给出参照物比长篇描述更有效**
- "类似 GitHub Issues 的列表页"比花 200 字描述列表样式更直观
- 但只用参照物做起点，随后补充差异点

## UI 设计工具 vs Vibe Coding 工具的差异

> 两类工具的 prompt 侧重已在 Step 2 选项中描述。选择后加载对应模板即可，无需重复说明差异。
>
> 如需快速判断：UI 设计工具关注**视觉外观**（间距、色值、组件样式），Vibe Coding 工具关注**实现方式**（技术栈、组件结构、状态管理）。

## 反例与黑名单

以下操作是**明确禁止**的危险动作，会导致生成的 UI prompt 质量低下或用户返工。

| # | 禁止操作 | 后果 | 正确做法 |
|---|---------|------|---------|
| 1 | 🔴 **未经 🔴 CHECKPOINT 确认直接生成逐页 prompt** | 整体方向错误，所有页面继承错误，导致大规模返工 | Step 3 生成整体方向后，必须展示给用户确认 |
| 2 | 🔴 **未经 Step 2 确认目标工具就生成 prompt** | UI 设计工具 prompt 缺少视觉细节，或 Vibe Coding prompt 包含不必要的像素级描述 | Step 2 必须使用 AskUserQuestion 明确用户选择 |
| 3 | **使用抽象描述代替具体示例** | 生成工具无法理解"展示用户信息"，输出随机且不可控 | 给出具体字段名、数据格式、布局比例（如"左侧 64px 头像 + 右侧三行信息"） |
| 4 | **省略示例数据** | 生成工具用占位符填充，布局测试不充分 | 提供 3-5 条有差异的示例数据（不同长度的名字、不同状态、不同数值） |
| 5 | **只描述静态画面，忽略状态** | 生成工具不知道如何处理空态、加载态、错误态 | 为每个数据展示区域说明空态、加载态、错误态、边界情况的处理方式 |
| 6 | **页面 prompt 依赖整体方向** | 用户单独复制一个页面 prompt 到工具时，缺少配色/字号/间距等 token | 每个页面 prompt 内联引用相关设计 token（色值、字号、间距），而非"参见整体方向" |
| 7 | **配色方案缺少精确 HEX 值** | 设计工具无法工作，只能输出近似色 | 至少提供主色、辅助色、背景色、文字色的 HEX 值；如 PRD 未指定，根据行业惯例推断并标注"推断配色" |
| 8 | **忽略平板断点** | 平板用户体验差，很多团队只设计桌面和移动端 | 响应式断点必须包含平板（通常 768px-1024px），说明布局策略 |
| 9 | **交互描述过于模糊** | "支持编辑和删除"无法让工具理解交互触发方式 | 使用因果句式："当用户点击 X 时，Y 发生"、"鼠标悬停在行上时，右侧出现编辑图标" |
| 10 | **一次性生成超过 10 个页面的 prompt** | prompt 过长，用户难以管理，生成工具可能截断 | 按优先级分批生成：先 P0 页面（3-5 页），确认后再继续 P1/P2 |

**特别警告**：UI 生成工具的质量高度依赖 prompt 的具体性和完整性。**宁可多写 100 字具体描述，也不要省 10 字导致输出随机。**
