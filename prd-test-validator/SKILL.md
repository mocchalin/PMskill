# PRD 测试用例生成与 Vibecoding 代码验证

本skill支持一个闭环流程：**PRD 评审 → 测试用例 → 代码审查 → 修复指令**。

四个阶段可独立使用，也可串联：
1. **阶段 A0（PRD 质量评审）**：以资深 QA 视角审视 PRD，找出缺失/矛盾/模糊/不可测/奇脉/依赖六类问题，列出清单和默认处理建议，**等用户确认后再继续**。
2. **阶段 A（用例生成）**：基于 PRD + A0 确认的补充场景，产出覆盖完整的测试用例 Excel。
3. **阶段 B（代码审查）**：用已生成的用例 + 四类检测维度，对 vibecoding 代码做审查，产出**审查报告 + 问题清单 Excel**。
4. **阶段 C（修复指令）**：用户在问题清单里勾选要修的问题，脚本自动生成 Cursor/Claude Code/通用 三种格式的修复指令，喂给 AI 编码工具自动修复。

## 什么是 "vibecoding 代码"

指用 AI 按自然语言描述快速生成的代码。它通常能跑通 happy path，但容易在以下四个方面翻车，这也是本skill检测的核心维度：

1. **需求覆盖度** — 验收标准/边缘场景是否真的实现了
2. **代码质量** — 空指针、越界、资源泄漏、异常吞掉、类型不安全
3. **安全** — 注入（SQL/命令/XSS）、鉴权绕过、敏感信息硬编码、不安全反序列化
4. **性能与并发** — N+1 查询、竞态条件、死锁、无限循环、阻塞主线程

## 判断要做哪个阶段

看用户输入和请求的组合：

| 用户提供 | 用户想要 | 走哪个阶段 |
|---------|---------|-----------|
| PRD 文档 | **只评审 PRD**（不生成用例） | 仅 A0 |
| PRD 文档 | 生成用例（含评审环节） | A0 → A |
| PRD 文档（要跳过评审） | 直接生成用例 | 仅 A（用户明确说不需评审才跳过） |
| 代码（+可选的已有用例） | 审查代码 | 仅 B |
| PRD + 代码 | 全流程 | A0 → A → B → C |
| 已有审查报告/问题清单 Excel | "让 AI 自动修复" | 仅 C |
| 代码 | 审查 + 生成修复指令 | B → C |

**默认行为**：收到 PRD 时，**先做 A0**，不要跳过。A0 通常能找出 5-15 个需求坑，省后期返工。只有用户明确说"PRD 已经很完善了，直接生成用例"或"我只要快速用例，不用评审"时才跳过。

## 阶段 A0：PRD 质量评审

### A0.1 读 PRD，以资深 QA 视角找问题

以一位 5+ 年测试经验的工程师视角审视 PRD，在下面六个维度逐项扫描（详见 `references/prd_review_checklist.md`）：

- **缺失**：PRD 完全没提但实现时一定要回答的问题（未登录场景、token过期、超时时长、字段长度等）
- **矛盾**：前后不一致、与常识冲突、跨模块打架
- **模糊**：用词含糊、缺具体指标（"快速响应"、"大量数据"、"友好提示"）
- **不可测**：无法用黑盒手段验证（"界面美观"、"内存占用降低"）
- **奇脉**：边界值、异常场景、并发、权限、数据边界的典型 case 缺失
- **依赖**：与第三方服务、内部系统、前后端契约的耦合点未说清

不要吹毛求疵。每条问题要能让用户立即判断"这是个真问题"，且能回答"改了会影响测试用例"。

### A0.2 给每条问题配一个默认处理建议

这是 A0 最关键的设计——**用户只需确认"接受/修改/拒绝"，不用每条都自己输入**。

每条问题给出的建议有四种类型：

| 建议类型 | 含义 | 适用场景 |
|---------|------|---------|
| **补全** | 用例中按某个合理默认生成新用例 | 奇脉、缺失类，有业界通用做法的 |
| **假定** | 采用一个默认值，不等 PRD 更新 | 模糊类，能猜到产品意图的 |
| **搁置** | 该场景暂不测，等 PRD 明确 | 重要但无法猜的 |
| **追问PM** | 必须先问产品，否则影响大 | 阻塞级矛盾或方向性缺失 |

**例子**：

```
问题：AC-2.1.2 未明确大小校验时机（前端/后端）
默认建议：【补全】同时生成前端（JS 拦截）+ 后端（413 响应）两个场景的用例
若确认将新增：
  • TC-NEW: 文件大小恰好50MB通过
  • TC-NEW: 文件大小50MB+1字节前端拦截
  • TC-NEW: 绕过前端的60MB请求后端返回413
```

把 Excel 放到 outputs 目录，`present_files` 展示。然后用 AskUserQuestion 工具确认：

```
问题：PRD 评审发现 {N} 个问题（🔴 {blocker} 阻塞 / 🟡 {major} 重要 / 🟢 {minor} 建议）。请确认下一步：
选项：
  - "全部接受默认建议，继续生成用例"
  - "我要修改部分决定（稍后发修改过的 Excel 或口头说明）"
  - "只做评审，不生成用例"
  - "先处理'追问PM'的问题再继续"
```

**同时给用户的话术模板（Excel 交付时附带）：**

> 每条都带了默认处理建议，分三种操作：
> - **接受**（√）：按建议执行，会在后续用例中自动补上
> - **修改**：你在"用户补充/覆盖说明"列写明不同方案
> - **拒绝**：你认为这不是问题，不处理
>
> 另外，有 N 个问题标记为"追问 PM"——这些是方向性问题，建议先和产品明确后再继续，但如果你愿意先用合理假定推进也可以。

### A0.5 等用户确认后读回决定

用户确认后会发来两种形式之一：
- **口头确认**（如"全部接受"、"除了 PR-003 都接受"、"PR-005 改为搁置"）：根据用户回复更新决定，记录在内部状态里
- **修改过的 Excel**：用脚本读回决定

```bash
python scripts/read_prd_review_decisions.py reviewed.xlsx
```

脚本输出 JSON 到 stdout，分 `accepted` / `modified` / `rejected` / `pm_pending` / `undecided` 五类。

**对每类的处理方针：**
- `accepted`：默认建议的所有 `default_new_cases` 纳入阶段 A 的用例生成
- `modified`：读取 `user_notes`，按用户的新方案生成对应用例
- `rejected`：不管它
- `pm_pending` 且用户未明确决定：在生成用例时**跳过这些场景**，但在最终的 PRD 补充建议文档里强调这些未决问题
- `undecided`：提醒用户还有 N 条未做决定，问是否全部按默认处理

## 阶段 A：从 PRD 生成测试用例 Excel

**如果来自 A0**：不仅要覆盖原 PRD 的 AC，还要把 A0 中用户"接受"和"修改"的 `new_cases` 融入用例表。这些新用例可用特殊 ID 前缀 `TC-NEW-` 标记，便于区分。

### A.1 读取并理解 PRD

先搞清楚 PRD 长什么样。根据文件类型：
- `.docx` → 读 docx skill 的操作说明再操作
- `.pdf` → 读 pdf skill 的操作说明再操作
- `.md` / `.txt` → 直接 `view`
- `.xlsx` 形式的需求 → 读 xlsx skill 的操作说明

**从 PRD 中抽取：**
- 功能模块（用于"所属模块"字段）
- 每个功能点的验收标准（acceptance criteria）
- 输入字段及其约束（类型、长度、范围、必填、格式）
- 业务规则与状态流转
- 非功能需求（性能指标、安全要求、兼容目标）

如果 PRD 写得模糊、没有明确的验收标准或字段约束，**不要编造数据**。先向用户列出抽取到的内容和存疑点，确认后再生成用例。编出来的"身份证号限制18位"如果 PRD 根本没说，就是在埋雷。

### A.2 设计用例（五种方法组合使用）

不要机械地把五种方法各写一遍。而是根据功能性质选合适的方法组合：

| 功能类型 | 主用方法 |
|---------|---------|
| 带输入字段的表单/接口 | 等价类 + 边界值 + 错误推测 |
| 有多个条件组合的业务规则 | 因果图 / 判定表 |
| 跨多步的业务流程 | 场景法（主流程 + 分支 + 异常流） |
| 状态机类功能 | 场景法 + 因果图 |
| 已知易错点（登录/支付/上传/权限） | 错误推测重点覆盖 |

五种方法的要点提醒（详见 `references/test_design_methods.md`）：
- **等价类划分**：有效等价类 + 无效等价类都要覆盖
- **边界值**：min-1, min, min+1, max-1, max, max+1；空、单字符、最大长度；数值 0、负、极大
- **因果图**：多条件组合爆炸时用，别穷举全排列，挑有意义的组合
- **场景法**：至少 1 条主流程 + N 条备选流程 + N 条异常流程
- **错误推测**：基于常见坑（并发、超时、重复提交、特殊字符、权限越权）

### A.3 每条验收标准必须 ≥1 正向 + ≥1 负向

这是硬要求。审视用例时逐条验收标准核对：
- 正向用例（positive）：符合条件 → 系统正常响应
- 负向用例（negative）：不符合条件 → 系统正确拒绝并给出合理提示

### A.4 异常场景必须覆盖这五类

对每个涉及网络请求/并发/权限/数据输入的功能，都要加上：
- **网络异常**：断网、弱网、请求中断
- **超时**：服务端慢响应、客户端超时
- **并发**：重复点击、并发修改同一资源、幂等性
- **权限**：未登录访问、越权访问（水平/垂直）、token 过期
- **数据边界**：空/超长/特殊字符/SQL/XSS/unicode/emoji

### A.5 兼容性矩阵

在 Excel 里加一个独立的 sheet "兼容性矩阵"，基于 PRD 中提到的目标用户/平台填充。如果 PRD 没说，给一个通用的默认值并在单元格备注里标"默认推荐，请根据实际目标用户调整"：

**Web 端默认矩阵：**
- 浏览器：Chrome 最新版、Firefox 最新版、Safari 最新版、Edge 最新版
- 操作系统：Windows 11、Windows 10、macOS 最新版、Ubuntu 22.04
- 分辨率：1920×1080、1366×768、2560×1440

**移动端默认矩阵：**
- iOS：最新版 + 前 2 个大版本 / iPhone 15、iPhone 13、iPhone SE
- Android：最新版 + 前 2 个大版本 / Samsung、小米、华为 各一款主流机型

### A.6 用例 ID 编号规范

格式：`TC-<模块缩写>-<序号3位>`，例如 `TC-LOGIN-001`、`TC-ORDER-042`。
同一模块的正向负向用例编号要能看出分组，不要随便跳号。

### A.7 优先级评定

- **P0**：主流程、支付/登录/注册、数据安全相关、阻塞性 bug 场景
- **P1**：常用次流程、重要边界条件、主要兼容场景
- **P2**：提示文案、极端边界、低频兼容场景、UI 细节

### A.8 生成 Excel

**使用打包好的脚本，不要自己手写 openpyxl：**

```bash
python scripts/generate_test_cases.py <cases_json> <output_xlsx>
```

其中 `cases_json` 是你整理好的 JSON 文件，脚本会负责：
- 创建"测试用例"sheet，含筛选 + 冻结首行 + 列宽自动适配
- 创建"兼容性矩阵"sheet
- 创建"用例索引"sheet（按模块/优先级统计）
- 优先级用颜色区分（P0 红、P1 黄、P2 绿底）
- 表头加粗 + 底色

详细的 JSON schema 和使用示例见脚本开头注释。

**用例表必备字段（顺序固定）：**

| 字段 | 说明 |
|-----|------|
| 用例 ID | TC-XXX-NNN |
| 所属模块 | 与 PRD 的模块对应 |
| 用例标题 | 一句话，动词开头，主谓清晰 |
| 优先级 | P0/P1/P2 |
| 用例类型 | 正向/负向/异常 |
| 测试设计方法 | 等价类/边界值/因果图/场景法/错误推测（可多选，用+连接） |
| 前置条件 | 账号状态、数据准备、环境准备 |
| 测试步骤 | 编号步骤，一步一行，使用 \n 换行 |
| 测试数据 | 具体的输入值，不要写"合法数据"这种虚的 |
| 预期结果 | 可观测、可判定，不要写"正常"、"OK" |
| 测试类型 | 功能/性能/安全/兼容 |
| 关联验收标准 | 对应 PRD 中的哪条 AC（如 AC-1.2） |

### A.9 🔴 CHECKPOINT — 交付前自检

生成 Excel 后用这个清单自查（本质上是"把自己当成用户"），然后用 AskUserQuestion 确认交付：

```
问题：测试用例 Excel 已生成，自检结果如下：
  ✅/❌ 每条验收标准至少 1 正 1 负
  ✅/❌ 五类异常场景（网络/超时/并发/权限/数据边界）都有覆盖
  ✅/❌ 没有"正常使用"、"数据合法"这种虚的预期结果
  ✅/❌ 测试数据是具体的值
  ✅/❌ P0 数量合理（一般 20-40%）
  ✅/❌ 兼容性矩阵 sheet 存在且不空
  ✅/❌ Excel 打开后表头冻结、可筛选

选项：
  - "确认交付，继续下一步"
  - "我要调整部分用例（说明具体问题）"
  - "需要补充更多场景覆盖"
```

## 阶段 B：用用例审查 Vibecoding 代码

### B.1 获取代码

代码可能以如下方式提供：
- 粘贴的片段 → 直接读
- 上传的文件 → `view`
- 仓库目录 → 先 `view` 目录结构，再挑关键文件读
- GitHub 链接 → 用 `web_fetch` 拿

### B.2 定位检查范围

如果有阶段 A 生成的用例表，优先"用例驱动"审查——对每条 P0/P1 用例，找代码里对应的实现，判断能否通过。

如果没有用例表，走"维度驱动"审查——按下文四个维度对代码进行静态审查。

### B.3 四维度检查清单

详细清单见 `references/code_review_checklist.md`，核心要点：

**维度 1：需求覆盖**
- 对照 PRD 的每条验收标准，找到对应代码
- 标记：✅已实现 / ⚠️部分实现 / ❌未实现 / ❓找不到对应代码
- 特别注意"静默失败"：代码看起来跑了但没真正完成需求

**维度 2：代码质量**
- 空值处理（null/undefined/None 检查）
- 边界条件（空数组、零、负数、最大值）
- 异常处理（有 try 但 catch 是空的？catch 了所有 Exception？）
- 资源管理（文件/连接/锁 是否释放）
- 类型安全（隐式转换、==/=== 混用、Python 字符串/字节混淆）

**维度 3：安全**
- 注入：SQL 字符串拼接、命令拼接、HTML 不转义输出
- 鉴权：接口是否有鉴权、越权检查
- 敏感信息：硬编码的 API key、密码、token
- 反序列化：`pickle.loads` 未校验来源、`eval`/`exec` 用户输入
- 密码/随机：`md5`/`sha1` 做密码、`random` 做安全令牌

**维度 4：性能与并发**
- N+1 查询（循环里查数据库）
- 不必要的全量加载（`SELECT *`、一次读全部文件到内存）
- 并发：共享状态无锁、锁粒度过大、死锁路径
- 阻塞：在 async 函数里用同步 I/O、主线程做 CPU 密集任务
- 循环：可能的无限循环、O(n²) 能降到 O(n) 的

### B.4 输出审查报告 + 问题清单 Excel

**双输出**：一份给人看的 Markdown 报告，一份给后续流程用的 Excel 问题清单。

#### B.4.1 Markdown 审查报告 `code_review_report.md`

结构：

```markdown
# Vibecoding 代码审查报告

## 摘要
- 审查文件数：X
- 严重问题：X 处（🔴）
- 一般问题：X 处（🟡）
- 建议优化：X 处（🟢）
- 总体结论：[可以上线/需修复后上线/建议重写]

## 一、需求覆盖
| 验收标准 | 状态 | 证据/问题 |
|---------|------|---------|
| AC-1.1 登录成功跳转 | ✅ | auth.py:45 |
| AC-1.2 密码错误提示 | ⚠️ | 只返回 401，没按 PRD 要求的文案 |
| AC-1.3 账号锁定 | ❌ | 代码中未实现 |

## 二、代码质量问题
### 🔴 [严重] 文件:行号 - 问题标题
**代码片段：**
```python
...
```
**问题说明：**（具体是什么问题，为什么是问题）
**修复建议：**（给出具体改法）

## 三、安全问题
（同上格式）

## 四、性能与并发问题
（同上格式）

## 五、建议用例覆盖
列出当前用例表中没有覆盖、但代码暴露出风险的场景，建议补充的用例。
```

如果是大仓库、问题很多，**不要试图一次列完**。按严重程度挑 TOP 10 严重问题深入分析，其他问题只列清单。用户可以再要求深入看某个。

#### B.4.2 问题清单 Excel `issues_checklist.xlsx`

这份 Excel 是连接阶段 B 和阶段 C 的桥梁：用户在 Excel 里勾选"要修哪些"，阶段 C 就能生成精确的修复指令。

**生成流程**：把审查中发现的每个问题整理成 JSON，然后用脚本：

```bash
python scripts/generate_issues_checklist.py issues.json issues_checklist.xlsx
```

**issues.json 的 schema**：

```json
{
    "project": "项目名",
    "code_reviewed": ["src/app.py", "src/auth.py"],
    "issues": [
        {
            "id": "ISSUE-001",
            "severity": "critical",
            "dimension": "安全",
            "file": "src/app.py",
            "line": "34-35",
            "title": "SQL 注入：INSERT 语句字符串拼接",
            "code_snippet": "cursor.execute(f\"...\")",
            "description": "问题的详细说明",
            "fix_suggestion": "参数化查询示例代码",
            "related_ac": "AC-2.1.1",
            "related_tc": "TC-UP-006"
        }
    ]
}
```

**字段要求：**
- `id`：全局唯一，建议格式 `ISSUE-NNN`
- `severity`：`critical` / `major` / `minor`（注意是英文小写，展示时自动转中文图标）
- `dimension`：`需求覆盖` / `代码质量` / `安全` / `性能并发`
- `file`、`line`：精确定位，方便 AI 工具直接跳到现场
- `code_snippet`：1-10 行关键片段，不要粘整个函数
- `fix_suggestion`：给到代码级建议，最好含"改前→改后"或示例代码

问题清单的每一条必须与 Markdown 报告里的条目一一对应——两者同源。

### B.5 🔴 CHECKPOINT — 报告交付

将 `code_review_report.md` + `issues_checklist.xlsx` 一起放到 outputs 目录，调用 `present_files` 展示。然后用 AskUserQuestion 确认下一步：

```
问题：代码审查完成，发现 {critical} 处严重 / {major} 处一般 / {minor} 处建议优化。请确认下一步：
选项：
  - "进入阶段 C：勾选问题清单后生成 AI 修复指令"
  - "深入查看某个具体问题"
  - "到此为止，不需要修复指令"
  - "补充审查范围（还有文件没看到）"
```

告知用户：若希望自动修复，可在 `issues_checklist.xlsx` 的"修复"列勾选 √，另存后进入阶段 C。

## 阶段 C：生成 AI 工具修复指令

### C.1 获取勾选后的 Excel

用户应该已经在 `issues_checklist.xlsx` 的"修复"列对想修复的问题填了 √（或 x / yes / 1 也识别）。拿到用户上传的 Excel。

如果用户跳过 B 直接给来一份审查报告或问题清单，确认一下：
- 如果是 markdown 报告 → 先帮他转成问题清单 Excel（走 B.4.2 流程）
- 如果已是勾选好的 Excel → 直接进 C.2

### 🔴 CHECKPOINT — 确认修复范围

生成修复指令前，用 AskUserQuestion 确认：

```
问题：已读取勾选项，共 {N} 个问题待修复（{critical} 严重 / {major} 一般 / {minor} 建议）。
  按文件分组：{file_count} 个文件受影响。
选项：
  - "确认，生成三种格式的修复指令"
  - "只要 Cursor 格式"
  - "只要 Claude Code 格式"
  - "只要通用 Markdown 格式"
  - "我需要调整勾选项"
```

确认后进入 C.2。

### C.2 生成三种格式的修复指令

脚本会按"文件"维度合并问题（同一文件多个问题 → 一个任务），同时输出三种格式：

```bash
python scripts/generate_fix_prompts.py <checked_xlsx> <output_dir> --project "项目名"
```

输出三份交付物：

**1. `fix_prompt_generic.md`** — 通用 Markdown
- 适合场景：不知道用户用哪个工具、或用户在 Copilot Chat / Windsurf / 各种 AI 对话框里复制粘贴
- 特点：纯 Markdown，自带使用说明和修复规则，最泛用

**2. `fix_prompt_cursor/` 目录** — Cursor 专用
- 包含 `.cursorrules`（Cursor 自动读取的规则文件）+ `.cursor-tasks/task_XX_<file>.md`（每个文件一个任务文件）+ `README.md`（使用说明）
- 用户把该目录复制到项目根，打开 Cursor，用 Cmd+L 发送 `请执行 .cursor-tasks/task_01_xxx.md` 即可
- 特点：一次配置长期生效，适合在真实项目中持续修复

**3. `fix_prompt_claude_code.md`** — Claude Code 适用
- 针对 Claude Code 的 Edit / MultiEdit 工具优化，推荐一次修一个文件，修完给 diff
- 用户用 `claude "按照 fix_prompt_claude_code.md 修复"` 即可启动
- 特点：对话式分步修复，每步可审查

### C.3 按文件分组的好处（为什么这么设计）

AI 编码工具处理代码时，**读文件开销远大于改文件**。如果把同一文件的 5 个问题拆成 5 个任务：
- AI 要 5 次读入该文件 → 浪费 token
- 5 次修改可能互相冲突（第 3 次修改可能撤销了第 1 次）
- 切换上下文容易遗忘前面的约束

合并成一个任务后：
- 读一次文件 → AI 在完整上下文里一次性修复所有问题
- MultiEdit 工具能原子完成多处修改
- 每个文件的修复互相独立，可以并行审查

### C.4 交付与后续

把三份输出都放到 outputs 目录下 `<项目>/fix-prompts/`，用 `present_files` 展示。

**告知用户使用方式：**

> 已生成三种修复指令格式：
> - Cursor：把 `fix_prompt_cursor/` 目录复制到项目根，Cursor 会自动加载规则
> - Claude Code：在项目根运行 `claude "按照 fix_prompt_claude_code.md 修复"`
> - 其他 AI：把 `fix_prompt_generic.md` 整段粘进对话框即可

**修复后的回归**：AI 修复完成后，建议用户回到阶段 A 生成的 `test_cases.xlsx`，跑一遍用例验证修复是否有效、是否引入了新问题。这样整个闭环就完整了：用例驱动审查 → 审查生成修复指令 → 修复后用用例验证。

## 失败模式速查表

### 阶段 A0（PRD 评审）

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| PRD 格式无法解析（加密 PDF、损坏 docx） | 提示用户转存为 .md 或粘贴全文 | 仅基于用户口头描述做评审，在报告中标注"未读原文" |
| PRD 过于简短（<500 字），六维度几乎无发现 | 扩大扫描范围：检查隐含假设、缺失的非功能需求 | 如实告知"PRD 过于概括，建议先补充再评审"，提供 PRD 骨架模板 |
| 用户拒绝所有评审发现（认为 PRD 无问题） | 举 2-3 个业界常见翻车案例对标 | 尊重用户决定，在交付文档中标注"未经评审补充" |
| 评审发现 >30 条（PRD 质量极差） | 按 severity 排序，只展示 blocker+major，minor 折叠 | 建议用户先修 PRD 再继续，提供修改优先级建议 |

### 阶段 A（用例生成）

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| PRD 无明确验收标准（AC 缺失） | 从功能描述反推验收标准，标注"QA 推断"请用户确认 | 仅基于功能名称生成通用冒烟用例，明确标注覆盖不足 |
| 用例数量爆炸（>500 条） | 按优先级裁剪：保留全部 P0、P1 抽样、P2 仅列大纲 | 分批交付：先交 P0 用例，P1/P2 按需追加 |
| 脚本执行失败（openpyxl 未安装） | `pip install openpyxl` 自动安装 | 手动生成 CSV 替代，标注格式损失 |
| 兼容性矩阵与 PRD 目标平台冲突 | 以 PRD 为准覆盖默认矩阵 | 生成两套矩阵（PRD 指定 + 推荐补充），让用户选择 |

### 阶段 B（代码审查）

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 代码量过大（>50 文件） | 按用例驱动：只审查 P0/P1 用例对应的文件 | 仅做目录结构分析 + 关键文件抽样，报告标注"部分审查" |
| 无对应测试用例（跳过阶段 A） | 切换为"维度驱动"审查，按四维度逐项检查 | 建议先回到阶段 A 生成用例，再做审查 |
| 代码使用了不熟悉的框架/语言 | 基于通用代码质量原则审查，标注"非框架专家" | 仅做安全和性能维度审查，跳过框架特定最佳实践 |
| 审查发现 0 个问题（代码看似完美） | 扩大检查范围：并发、边界、依赖版本、配置安全 | 如实报告"静态审查未发现明显问题"，建议做动态测试 |

### 阶段 C（修复指令）

| 触发条件 | 一线修复 | 仍失败兜底 |
|---------|---------|-----------|
| 用户未勾选任何问题 | 提示"请先在 Excel 修复列勾选 √"，重新上传 | 默认选择所有 critical 问题生成修复指令 |
| Excel 格式损坏 / 无法读取 | 尝试用 pandas 容错读取，跳过损坏行 | 请用户重新导出，或口头告知要修哪些 |
| 修复指令生成后用户说"AI 工具无法识别" | 检查目标工具版本，调整指令格式（如 Cursor 新旧格式差异） | 提供通用 Markdown 格式作为保底 |
| 同一文件问题 >10 个（合并后指令过长） | 拆分为 2-3 个批次，每批 ≤5 个问题 | 按 severity 排序，critical 优先修复，minor 单独一批 |

## 反例与黑名单

以下是执行本 skill 时常见的错误做法，**必须避免**：

| # | 反例 | 正确做法 |
|---|------|---------|
| 1 | 编造 PRD 中未提及的字段约束（如"身份证号 18 位"） | 标注"QA 推断"并请用户确认，或直接追问 |
| 2 | 跳过 A0 直接生成用例（除非用户明确要求） | 默认先做 A0 评审，A0 通常能发现 5-15 个需求坑 |
| 3 | 预期结果写"正常显示"、"功能正常" | 写具体可观测的结果："返回 200，body 含 user_id 字段" |
| 4 | 测试数据写"合法数据"、"有效输入" | 写具体值："账号: testuser01，密码: P@ssw0rd!" |
| 5 | 全标 P0（失去优先级区分意义） | P0 一般占 20-40%，主流程/安全/支付为 P0 |
| 6 | 代码审查时一次列完所有问题（大仓库） | TOP 10 严重问题深入分析，其余仅列清单 |
| 7 | 修复指令不合并同文件问题 | 按文件分组，同一文件的多个问题合并为一个任务 |
| 8 | A0 评审发现全部接受、不问用户就继续 | 必须经过 🔴 CHECKPOINT 确认后才能进入阶段 A |
| 9 | 安全维度只检查 SQL 注入 | 同时检查命令注入、XSS、鉴权绕过、硬编码密钥、不安全反序列化 |
| 10 | 对 vibecoding 代码过于宽容 | vibecoding 代码恰恰需要更严格的审查，因为它常"看起来能跑但埋着雷" |
